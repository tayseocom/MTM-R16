## MTM-R16 — Web MIDI Sequencer Architecture

**Version:** 0.1  
**Maintainers:** Core engineering team  
**Last updated:** 4 Oct 2025

## 1. Purpose

This document defines the high-level architecture of the MTM-R16 web-based MIDI sequencer.  
It serves as the single source of truth for:
- System boundaries and modules
- Threading and timing model
- Data flow between UI, engine, storage, and hardware
- Performance and reliability expectations

---

## 2. Design principles

1. **Deterministic timing** – All MIDI events scheduled with sub-2 ms jitter.  
2. **Hardware immediacy** – Every control provides immediate visual feedback.  
3. **Separation of concerns** – Engine, UI, and storage are independent modules.  
4. **Browser-portable** – Runs on Chromium, Edge, and Safari (Web Audio + MIDI).  
5. **Offline-first** – All persistence local to IndexedDB; no external servers.  
6. **Testable** – Each subsystem mockable for headless testing.

## 4. Module summary

### 4.1 ui/
Front-end components and layout.

- **Framework:** Svelte (or React if preferred).  
- **Responsibilities:**  
  - Render panel (buttons, LEDs, LCD).  
  - Map keyboard/touch to engine actions.  
  - Animate state changes (< 50 ms latency).  
  - Display warnings, tempo, and mode text.  
- **Interface:** Publishes user actions as events via `uiBus`.

### 4.2 runtime/
Bridges UI and engine.

- Event router: translates UI gestures → engine method calls.  
- Central state store (`sequencerStore`) observable by both UI and engine.  
- Implements undo stack and temporary pages (Quantise, Erase, etc.).  
- Emits global notifications to UI (`ui:status`, `ui:toast`).

### 4.3 engine/
Core sequencing logic.

Sub-modules:

| Sub-module | Role |
|-------------|------|
| **transport** | State machine: Stop / Count-In / Play / Record. |
| **clock** | Internal timer & tempo ramping; delegates tick scheduling to AudioWorklet. |
| **sequencer** | Maintains Parts, Songs, playhead position, and loop boundaries. |
| **recorder** | Captures MIDI events, enforces filters, commits to storage. |
| **transform** | Quantise, transpose, copy, merge, erase. |
| **undo** | Stack of reversible frames with diff metadata. |

### 4.4 midi/
Hardware I/O layer.

- Requests `navigator.requestMIDIAccess` with optional sysex.  
- Enumerates and monitors ports (`onstatechange`).  
- Routes inbound events to recorder or transport control.  
- Sends outbound events with timestamps from scheduler.  
- Manages clock roles (master / slave).  
- Handles panic (`All Notes Off` + `CC64 = 0` on ch 1–16).

### 4.5 audio/
AudioWorklet + metronome.

- 44.1 kHz sample clock used as canonical timeline.  
- Schedules MIDI events by absolute `currentTime`.  
- Generates click sounds for count-in and metronome.  
- Reports jitter stats to `engine/clock`.

### 4.6 storage/
IndexedDB persistence.

- Stores Projects, Parts, Songs, Tracks, and EventChunks.  
- Manages autosave, migration, and undo logs.  
- Serialises to `.mtmproj` JSON or SMF export.  
- Provides async APIs (`getPart`, `saveTrackChunk`, etc.) returning Promises.  

### 4.7 workers/
Optional Web Workers for heavy transforms (quantise, merge).

- Off-main-thread compute to avoid UI stalls.  
- Communicates via `postMessage({ type:'applyTransform', payload })`.  
- Worker replies with a diff; engine commits via storage API.

## 5. Threading model

| Thread | Components | Purpose |
|---------|-------------|----------|
| **Main thread** | UI, Runtime, Engine orchestration | Event routing, rendering, I/O setup |
| **AudioWorklet thread** | Scheduler, Click | Sample-accurate timing, low jitter |
| **Web Worker (optional)** | Transforms | Heavy edits, undo diff generation |
| **IndexedDB thread** | Storage | Asynchronous, auto-batched by browser |

Communication:
- Engine posts timing events to UI (`tick`, `bar`, `songStep`) via `postMessage`.
- UI sends control messages to engine (`play`, `stop`, `recordArm`, `quantise`).
- All cross-thread messages serialisable JSON; no shared objects.

## 6. Event flow summary

**Example: recording one Part**

1. User presses `REC`.  
2. UI → `runtime` → `engine.transport.startRecord()`.  
3. Engine arms track, enters `COUNT_IN`, posts state to UI.  
4. AudioWorklet tick triggers after count-in; engine streams incoming MIDI from `midi/` into recorder.  
5. Recorder buffers events; on punch-out, commits to `storage/`.  
6. Storage writes new EventChunks; updates store; UI refreshes LED state.

## 8. Performance targets

| Metric | Target |
|---------|--------|
| MIDI scheduling jitter | ≤ 2 ms p95 |
| UI feedback latency | ≤ 50 ms |
| Max recorded notes per project | 11 000+ |
| Autosave interval | 1–2 s idle |
| IndexedDB write | < 20 ms per chunk |
| CPU load @ 120 BPM, 8 tracks | < 15 % on M1 Air |

---

## 9. Error handling & recovery

- **Device loss:** pause transport, display amber LED, resume on user input.  
- **Low memory:** flash REC LED, stop safely at next beat.  
- **Database error:** prompt “Reload to recover”.  
- **Unhandled promise:** captured globally and logged with timestamp.

## 10. Extensibility hooks

- Plug-in transforms (`registerTransform(name, fn)`).  
- Alternative clock sources (BLE, OSC, future Ableton Link shim).  
- Remote sync via WebRTC data channel (experimental).  
- Theme overrides through CSS variables defined in `design_guidelines.md`.

---

## 11. Security & privacy

- No cloud sync.  
- MIDI data and SysEx dumps never transmitted externally.  
- Browser storage only; user-initiated export required for sharing.  
- CSP: no external scripts, inline hashes only.
